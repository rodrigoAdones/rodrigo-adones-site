# 0005: CI/CD — GitHub Actions with Wrangler Deploy

**Status:** Proposed
**Date:** 2026-09-15

Recommendation: accept, as originally proposed, with quality gates added.

## Context

Two ways to get from a push to a deployed site: let Cloudflare's git integration build it, or build
it in GitHub Actions and deploy the artifact with Wrangler. The original proposal was Actions.

## Options Considered

- **Cloudflare-side build via git integration** — zero config, but there is nowhere to put
  quality gates: a post reaches production the moment it is pushed.
- **GitHub Actions builds, Wrangler deploys** — you own the pipeline, so checks run before
  anything reaches production, and PR previews are possible.

## Decision

GitHub Actions owns the build; Wrangler performs the deploy.

Rationale: gates are wanted, and a Cloudflare-side build gives nowhere to put them. Building in
Actions means a post cannot reach production without passing checks — which matters precisely
because posts will be published tired, on a Sunday night, from a phone (N2).

### Pipeline

**On pull request**

1. `pnpm install --frozen-lockfile`
2. Build (`astro build` — this is where frontmatter schema validation fires,
   [0002](0002-content-model.md))
3. `astro check`, plus the repo's existing `pnpm lint` and `pnpm test`
4. Broken-link check over `dist/` (lychee or linkinator), internal links only
5. `wrangler versions upload` → comment the preview URL on the PR

**On push to `main`**

1. Steps 1–4 above
2. `wrangler deploy`
3. Optional: ping the sitemap / notify the newsletter provider

Keep it to those gates. A 12-step pipeline on a personal blog is the same over-engineering as
[0003](0003-build-strategy.md) in a different costume. Add Lighthouse CI only if performance
actually regresses; do not add it pre-emptively.

### Authoring loop (serves N2)

Draft in a branch → open a PR → **read the actual rendered post at the preview URL** → merge.
This is the whole reason to bother with previews: proofreading rendered output catches things
proofreading markdown does not, and it works from a phone browser.

Secrets: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository secrets, token scoped
to Workers deploy only.

## Consequences

- You own the build. When a dependency breaks the build, it breaks in CI where you can see it,
  rather than inside a vendor's build container.
- **Side benefit worth naming:** this repo becomes a legitimate, low-stakes place to instrument
  the delivery metrics under study. Deploy frequency and lead time for changes are directly
  derivable from `git` and the Actions API here, with no corporate politics attached. "I
  instrumented four keys on my own publishing pipeline" is a small, concrete, numbered artifact —
  and it is on-thesis.

## Reference config

**`.github/workflows/deploy.yml`**

```yaml
name: Deploy
on:
  push:
    branches: [main]
concurrency:
  group: deploy
  cancel-in-progress: true
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm build          # frontmatter schema validation fires here
      - run: pnpm astro check
      - run: pnpm lint
      - run: pnpm test
      - name: Check internal links
        run: pnpm exec linkinator ./dist --recurse --skip "^https?://"
      - name: Assert feed is valid and current
        run: node scripts/check-feed.mjs    # 0007 mitigation
      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: deploy
```

`pr.yml` is the same through the link check, then `command: versions upload` and a comment with
the preview URL — the proofreading loop above.

# 0005: CI/CD — GitHub Actions with Wrangler Deploy

**Status:** Accepted
**Date:** 2026-09-15 (accepted 2026-09-21)

Recommendation: accept, as originally proposed, with quality gates added.

## Context

Two ways to get from a push to a deployed site: let Cloudflare's git integration build it, or build
it in GitHub Actions and deploy the artifact with Wrangler. The original proposal was Actions.

## Options Considered

- **Cloudflare-side build via git integration** — zero config, but there is nowhere to put
  quality gates: a post reaches production the moment it is pushed.
- **GitHub Actions builds, Wrangler deploys** — you own the pipeline, so checks run before
  anything reaches production, and PR previews are possible.

## Decision

GitHub Actions owns the build; Wrangler performs the deploy.

Rationale: gates are wanted, and a Cloudflare-side build gives nowhere to put them. Building in
Actions means a post cannot reach production without passing checks — which matters precisely
because posts will be published tired, on a Sunday night, from a phone (N2).

### Pipeline

**On pull request**

1. `pnpm install --frozen-lockfile`
2. Cheap gates first, none of which need `dist/`: `pnpm lint`, `pnpm test`, `astro check`
3. Build (`astro build` — this is where frontmatter schema validation fires,
   [0002](0002-content-model.md))
4. Broken-link check over `dist/` (linkinator), internal links only; feed check
   ([0007](0007-newsletter.md))
5. `wrangler versions upload` → comment the preview URL on the PR

**On push to `main`**

1. Steps 1–4 above
2. `wrangler deploy`

Nothing after the deploy. There is no sitemap ping — Google and Bing retired those endpoints;
search engines discover the sitemap from `robots.txt`. Notifying the newsletter provider is
[0007](0007-newsletter.md)'s concern, and it is feed-driven rather than a pipeline step.

Keep it to those gates. A 12-step pipeline on a personal blog is the same over-engineering as
[0003](0003-build-strategy.md) in a different costume. Add Lighthouse CI only if performance
actually regresses; do not add it pre-emptively.

### Authoring loop (serves N2)

Draft in a branch → open a PR → **read the actual rendered post at the preview URL** → merge.
This is the whole reason to bother with previews: proofreading rendered output catches things
proofreading markdown does not, and it works from a phone browser.

**The branch is the draft.** The preview is produced by `astro build`, in which
`import.meta.env.PROD` is true, so `getPublishedPosts()` ([0002](0002-content-model.md)) drops
any post marked `draft: true` — a post flagged that way would be the one thing missing from its
own preview. A post in a PR therefore carries `draft: false`; the PR is what keeps it out of
production. `draft: true` is reserved for the rare case of deliberately merging an unfinished
post to `main`. This also keeps the preview byte-identical to what `main` will deploy.

Preview URLs are public: the rendered post is world-readable at an unguessable
`*.workers.dev` URL before it is merged. Acceptable for a blog; do not put anything in a PR
that must stay private. The Worker needs its `workers.dev` subdomain enabled for previews to
resolve.

Secrets: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository secrets, token scoped
to Workers deploy only.

## Consequences

- You own the build. When a dependency breaks the build, it breaks in CI where you can see it,
  rather than inside a vendor's build container.
- **Side benefit worth naming:** this repo becomes a legitimate, low-stakes place to instrument
  the delivery metrics under study. Deploy frequency and lead time for changes are directly
  derivable from `git` and the Actions API here, with no corporate politics attached. "I
  instrumented four keys on my own publishing pipeline" is a small, concrete, numbered artifact —
  and it is on-thesis.

## Reference config

**`.github/workflows/deploy.yml`**

```yaml
name: Deploy
on:
  push:
    branches: [main]
permissions:
  contents: read              # least privilege; the deploy needs nothing from GitHub but the checkout
concurrency:
  group: deploy
  cancel-in-progress: true
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v5
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm test
      - run: pnpm astro check
      - run: pnpm build          # frontmatter schema validation fires here
      - name: Check internal links
        run: pnpm exec linkinator ./dist --recurse --skip "^https?://"
      - name: Assert feed is valid and current
        run: node scripts/check-feed.mjs    # 0007 mitigation
      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: deploy
```

**`.github/workflows/pr.yml`** is the same through the feed check, with these differences:

```yaml
on:
  pull_request:
permissions:
  contents: read
  pull-requests: write        # to post the preview comment
# ...
      - id: preview
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: versions upload
      - uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: "Preview: ${{ steps.preview.outputs.deployment-url }}"
```

`wrangler versions upload` prints a `Version Preview URL:` line, which `wrangler-action` exposes
as the `deployment-url` output; a sticky comment keeps one up-to-date link per PR instead of one
per push.

**Dependencies** (dev): `@astrojs/check` and `typescript` for `astro check`; `linkinator`;
`wrangler`. Action majors are pinned to the current ones at time of writing; a `github-actions`
entry in `.github/dependabot.yml` keeps them fresh without growing the pipeline.
